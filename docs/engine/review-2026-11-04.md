# Architecture review: ThunderClap engine at 0.2.0-alpha.1 (2026-11-04)

External review brought by the user; adopted as D-044. Kept verbatim below.

Reviewed against `packages/engine/ARCHITECTURE.md`, D-041 and the refactor plan. Scope is the engine's shape, not Gate 2 product work.

## What is right and must be protected

- **Package boundary.** `@thunderclap/engine` with a per-module exports map, a boundary check that stops games importing internals, and `ARCHITECTURE.md` stating each contract as *today* vs *planned* with its phase. This is the promotion gate; keep it current on every public API change.
- **Host.** `Host { kind, embed, openExternal, copyText, clipboardWriteAllowed, fullscreen, storage, window? }`. Storage is probe-on-open and never throws, so a blocked itch iframe degrades instead of crashing. `createWebHost` and `createElectronHost` satisfy the same type. This is the seam shape the plan asked for.
- **Layout.** Pure functions (`classifyFormFactor`, `resolveTracks`, `resolveLayout`, `effectiveInsets`) plus a thin DOM binding (`createLayout`). Four form factors, named regions, `hidden`, and a `free` escape hatch with zero engine uses. Unit-testable without a browser.
- **Gestures.** Beside the action map, same tick model, same `blocked()`, bindable as actions. `magnify` (loupe + snap) is an engine option. A second game gets touch precision for free.
- **`createGame()` is generic.** `EngineCtx<A, S, C>` holds no nouns; `GameCtx extends EngineCtx` adds them. Correct layering.
- **Test ownership (D-041 add. 2).** Engine proves platform capability once on the device matrix; the game tests product. This keeps the engine honest when a second consumer arrives.

## Debt, in priority order

1. **Two overlays.** `ctx.ui` is the legacy 1920×1080 scaled overlay; `ctx.chrome` is the CSS-px one, active on phones only, and panel/toast layers are physically moved between roots when `active` flips. Desktop and iPad still run on design-px DOM. Two coordinate systems in every scene that cares. The plan's end state was CSS px everywhere with the scaled path deleted; that slipped past Gate 2.
2. **Phone concepts in `EngineCtx`.** `device: DeviceMode` (marked interim) and `fillBands` / `setFill(key)` (D-040's fill-and-crop) are Last-Rune-shaped ideas in the engine. Both belong to Layout's `freeRect` plus the Phase 3 `Camera.fitRect`, then get deleted.
3. **No camera.** `render/` still has the 2D x/y/zoom `Camera`. Layout computes `freeRect` but nothing consumes it. This is why dense phone boards are unsolved after zoom-removal; Phase 3 is the missing half of Phase 2, not only 3D readiness.
4. **`createGame` is a fixed pipeline.** Post, particles, audio, pad nav and the loop order (input → padNav → update → particles → scenes) are hard-wired, and `GameLoop` owns rAF. Fine for a second 2D game. 3D and XR need the renderer to take `(camera, target)` and the host to schedule frames.
5. **Host has no frame source.** The XR seam needs `Host` to provide `requestFrame` (rAF on web, `XRSession.requestAnimationFrame` later). Add it before extraction so XR is an implementation of `Host`, not a redesign.

## Calls

- **Deleting the legacy overlay is a Phase 3 entry condition, not refactor debt.** Phase 3 touches every scene's draw path; that is the cheapest moment to remove the second coordinate system. Do not start `ws/camera` until `ctx.ui` is CSS px on every form factor and `createCssChrome` is gone.
- **Phase 3 absorbs items 2 and 3.** `ws/camera` delivers `fitRect` fed by `layout.freeRect` and deletes `device` and `fillBands` from `EngineCtx` in the same branch.
- **Item 4 and 5 are Phase 3 `ws/render-call` scope.** `Renderer.render(frame, camera, target)`; `Host.requestFrame`; `GameLoop` takes the frame source from the host. Log the `Host` interface change in DECISIONS and `CHANGELOG.md`.
- **No Forgewilds work on the engine until Gate 3.** It would inherit the two-overlay model and the fixed pipeline.
